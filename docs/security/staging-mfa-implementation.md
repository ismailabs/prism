# Mandatory MFA staging implementation — 18 October 2026

Scope: PR #6 development and isolated `zwqcdfzfsudqccclficx` only. Production is not authorized. This does not implement breached-password rejection or accept the residual risk.

The new financial guard requires a live, unexpired AAL2 session, a current approved native TOTP factor, two approved verified factors, confirmed email and matching ownership. Approval requires native recent mailbox proof and recent TOTP verification. A Free Custom Access Token hook rejects unapproved factor activation without independent mailbox proof; native transaction rollback must pass the real Auth test before hosted activation. Previously activated accounts cannot restart enrollment after losing all approved factors.

Replacement requires an existing approved factor plus fresh mailbox proof. Native un-enrollment remains possible, but losing either of the last two approved factors closes financial access. Losing every factor has no email-only or administrative recovery bypass. Independent physical custody cannot be established by software; the acknowledgement is not human-test evidence. Total-loss recovery and public-release acceptance remain BLOCKED.

Financial Realtime publication is removed; Data API ownership/RLS remains authoritative. Sessions expire for financial access after 24 hours; deletion additionally requires TOTP proof from the last five minutes. Existing user IDs, financial owner IDs and verified factors are preserved.

Email confirmation and secure email change remain enabled. Staging now requires 16-character new passwords with letters/digits, secure password change, the current password when updating an existing password, and 600-second, eight-digit email actions. Email and Google providers remain enabled. Existing passwords are not rewritten.

## Remaining acceptance boundaries

- Fresh hosted enrollment, hosted first-activation rollback and real inbox delivery need an authorized synthetic browser session with a genuine CAPTCHA and delivered mail. CAPTCHA was preserved, not disabled to manufacture a positive test. The positive owner Google evidence remains historical; provider-neutral SQL checks do not pretend to be a new Google human test.
- A person must actually verify that their approved backup remains accessible after losing the primary device. Two distinct server secrets and a checkbox cannot prove physical independence. A securely stored offline copy can restore a surviving approved factor into a compatible authenticator, without an administrative override.
- Losing every approved factor and every copy leaves financial access, export and in-app account deletion locked. New mailbox proof cannot restart an activated account. No safe automatic all-factor-loss procedure has been established. Public recovery acceptance remains BLOCKED; operator handling of privacy/erasure requests also requires a defined process.
- Native recovery-code endpoints were read-only probed on the local version and returned 404. No codes were generated, and no hosted Free-plan entitlement is assumed. This implementation uses supported TOTP backup factors.
- Reused breached passwords are still accepted where they meet configured password rules. MFA is a separate compensating control. Mailbox plus password/Google compromise before first enrollment, phishing, stolen live AAL2 sessions, local device compromise and denial of service remain possible. Revocation stops new financial API access; it cannot retract information already displayed or copied. A stolen valid AAL2 session may retain financial access until revocation or the 24-hour limit, and sensitive operations require five-minute TOTP proof.
- AAL1 Auth sessions can still access their own Auth metadata and may create unverified factors or cause session disruption. The guard protects financial resources, not every provider account action. Native removal can cause lockout; it cannot restore financial access with fewer than two approved factors.
- Free-plan availability/quotas, SMTP suitability, genuine CAPTCHA expiry/replay, private Google client/audience evidence, physical-device/assistive-technology observations, independent recovery custody and operator responsibility remain applicable release requirements. No paid resource or replacement identity system is introduced.
- The existing build dependency chain currently reports five high-severity development-tool advisories involving `braces`/Tailwind 3. These are not native Auth or runtime financial exposure, but are retained as an unresolved release dependency issue; no unreviewed Tailwind major upgrade was applied.

## Transition and containment

Existing user IDs, financial rows and verified factors are retained. Existing password and Google sessions are locked out of financial tables until the new approval requirements are met. Existing native factors need independent mailbox approval, not an identity migration. Recovery with one approved factor requires mailbox proof, approved-factor verification, a tested replacement and two approvals before financial access resumes.

The prior immutable staging deployment and pre-change guard definitions are retained. Native migration tests inject transactional failures and verify catalogue rollback and unchanged financial history before successful replay. The local cold-restore drill deliberately populates approval audit and expired management state, restores every public/Auth/private table exactly, and checks approval/activation preservation, expired-window denial and sticky total-loss lockout. A transactional containment drill replaces only the financial guard with false, tests all 44 protected table/view surfaces and sensitive operations, verifies unchanged rows/history, then restores the exact guard/hook/ACL definitions and original approved access. These are disposable PostgreSQL SQL fixtures, not hosted recovery or physical-custody evidence.

Do not restore the old optional-MFA guard merely to regain access. An emergency rollback must keep financial access closed and preserve approval/history tables; production recovery and release require separate review. No production rollback has been executed because production was not changed. See [the recovery and containment runbook](mfa-recovery-runbook.md) for the existing-user transition and remaining operator decisions.

No original launch gate is marked PASS by this implementation. Residual-risk, recovery and production-release acceptance remain the product owner's decisions.
